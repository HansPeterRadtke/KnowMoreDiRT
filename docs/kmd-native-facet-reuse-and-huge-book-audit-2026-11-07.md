# Audit: existing KnowMoreDiRT facets and real-book recursion

Date: 7 November 2026. This is a read-only architecture and test audit; it does not start a second model worker or create a second database.

The existing native KMD content pipeline already supports document summaries, topic facets, keywords, keyphrases, entities, strengths, normalization, individual embeddings, native original-file links, and storage in content_representations. Its constrained schemas are FILE_ANALYSIS_SCHEMA and chunk_analysis_schema_for_keys in src/file_system_catalog/content_pipeline.py. It uses normalize_analysis and flatten_representations and is exercised by tests/filesystem_database/test_content_pipeline.py, including a real native SQLite catalog with simulated analysis.

In contrast, the active Raspberry Pi overview worker uses RawOnlyAnalysisStub, and the complete recursive summary worker currently requests only one JSON string named summary. As a result, all native generated representation records at the audit checkpoint were either summary or summary_long; there were zero keyword, keyphrase, topic, entity or description representations. The source metadata keyword placeholder is not equivalent to generated semantic keywords. Native generated keyword/kind rows can be stored with the existing schema, but the current summary search deliberately filters to summary kinds, so it would need to recognize them before keyword vectors affected rankings.

Two real local-Qwen trials on the complete Hick's Law source tested the original schema without writing the production database. The stock native chunk prompt returned a summary and five facets, but twenty descriptions and no keyword or keyphrase kinds. An explicit additional instruction to use the existing keyword and keyphrase enum kinds returned a summary, six facets, four keywords and fourteen keyphrases in one schema-constrained call. The original normalize_analysis and flatten_representations functions processed the returned data.

The native AnalysisClient.complete currently ignores max_tokens and uses all remaining context capacity for structured generation. That may be appropriate for native standalone facets but cannot be assumed safe when a complete-book hierarchy explicitly reserves generation room. Reusing the schema and normalization is preferable to inventing a competing mechanism; output reservation and combined structured generation still need real-model testing for large source groups.

Actual Qwen recursive summarization was proven on a 200,796-character original research paper, whose three contiguous source-level summaries were combined into one full-source root. The original KMD FileDB stores and retrieves all four vectors; full original/derived checksums, every summary source span, and parent/child links were independently verified. Another smaller RFC also used three leaves and one parent.

The complete 2,752,515-character HCI textbook was processed in a synthetic deterministic source-coverage test at a modeled 16,384-token context with 320 output and 384 safety tokens. It contained 830 source sections, 47 first-level groups and 48 total simulated summaries, including one root covering all source characters. All hierarchy invariants passed without production writes. This proves the planner and recursive tree can cover a huge book structurally, but it is **not** a real-Qwen full-book or factual-summary-quality test. No complete multi-million-character source was yet seen in the live indexed database.

The full-book root is intentionally compact because the active multilingual E5 embedding model only reads 512 input tokens. Detailed chapter queries should use the source and intermediate summary vectors rather than assuming a single short root summary can preserve every rare fact.

Known-topic summary queries work for many indexed originals, but unrelated questions still return nearest neighbors, not guaranteed relevant results. Fixed cosine thresholds, keyword score gaps, and an experimental rank blend were evaluated on heldout questions and found insufficiently reliable. These changes were not deployed.

Next required bridge: use the *existing* KMD facet schema and normalization within each bounded recursive summary LLM call; embed and store native keyword and keyphrase rows alongside every source-linked summary and parent node, and extend the query implementation to consider those rows. It must be tested before enabling on the continuously running worker. This report does not claim that bridge is complete.
